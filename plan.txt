Master context prompt
Paste this at the start of every agent session so each phase follows the same architecture and rules.
You are a senior Python and React engineer helping me build "Fitness Coach", a coaching app that combines exact math with retrieval-augmented answers from my library of PDF guides.

ARCHITECTURE
- Backend: FastAPI + SQLModel (SQLite now, PostgreSQL later) + FAISS. Frontend: React + Vite + TypeScript.
- Five backend modules under backend/app/modules/: user, nutrition, exercises, progressive_overload, rag_core. Shared config and database code live in backend/app/core/.
- backend/main.py mounts one APIRouter per module. Each module has router.py (thin HTTP layer), service.py (logic) and models.py or schemas (SQLModel and Pydantic types). Extra files: nutrition/calculator.py, exercises/catalog.py and generator.py, progressive_overload/algorithms.py, rag_core/engine.py and router_agent.py.
- Endpoints: /api/user/*, /api/nutrition/*, /api/exercises/*, /api/overload/*, /api/chat and /api/chat/stream.

NON-NEGOTIABLE RULES
1. Numbers come from Python, never from the LLM. TDEE, macros, volume and progression targets are pure functions with unit tests. The LLM only explains them.
2. RAG chunks carry metadata: category ('nutrition' or 'exercise'), source file, page. Nutrition code retrieves only category 'nutrition'; exercise code retrieves only category 'exercise'.
3. No business logic in routers. Modules talk to each other only through service.py functions.
4. Type hints everywhere, Pydantic validation on every request, clear HTTP errors (422 bad input, 404 missing record).
5. Store weights in kg internally; convert pounds on input and output.
6. Any health-related answer includes a short note that it is general information, not medical advice.

HOW TO WORK
- Before coding, list the files you will create or change. Then implement only what the current prompt asks.
- Write pytest tests for every function you add. Run the full test suite and show me the result before you say you are done.
- Do not add dependencies the prompt does not mention without asking me first.
- If something is ambiguous, ask me one concise question instead of guessing.
- Finish with: files changed, tests run, anything left undone.

Prompt 2.1: Calculator
Build the deterministic core of Module 2 (Nutrition) in app/modules/nutrition/calculator.py. Pure functions only: no database, no FastAPI, no LLM.

1. bmr_mifflin_st_jeor(sex, weight_kg, height_cm, age): 10*weight_kg + 6.25*height_cm - 5*age, then +5 for male or -161 for female.
2. bmr_katch_mcardle(weight_kg, body_fat_pct): 370 + 21.6 * lean_mass_kg, where lean_mass_kg = weight_kg * (1 - body_fat_pct/100).
3. choose_bmr(...): use Katch-McArdle when body_fat_pct is given, otherwise Mifflin-St Jeor. Return the value and the name of the formula used.
4. tdee(bmr, activity_level): multipliers sedentary 1.2, light 1.375, moderate 1.55, very_active 1.725, extreme 1.9.
5. target_calories(tdee, goal, sex): adjustments as named constants at the top of the file: fat_loss -20 percent, hypertrophy +10 percent, strength +5 percent, athletic_performance 0 percent. Enforce a floor of 1500 kcal for male and 1200 kcal for female, and report when the floor was applied.
6. macro_targets(target_kcal, weight_kg, goal, somatotype): protein 2.0 g/kg (2.2 for fat_loss); fat at least 0.8 g/kg and at least 20 percent of calories; carbs fill the remaining calories (protein 4, carbs 4, fat 9 kcal per gram). Somatotype tweak as editable constants: endomorph moves 5 percent of target calories from carbs to fat; ectomorph moves 5 percent from fat to carbs but never below the fat floor; mesomorph no change.
7. A frozen dataclass MacroResult with bmr, bmr_formula, tdee, target_kcal, protein_g, carbs_g, fat_g, floor_applied and a warnings list.

Tests: hand-computed cases for both formulas, every activity level, the calorie floor, macros summing to within 2 kcal of the target, and rejection of nonsense input (negative weight, body fat above 60).

Prompt 4.2: Progression algorithms
Build the progression engine in app/modules/progressive_overload/algorithms.py as pure functions that take plain data and return plain data.

1. double_progression(last_session_sets, rep_range, increment_kg, rpe_ceiling):
   - If every working set reached the top of rep_range at RPE at or below rpe_ceiling (default 8.5): recommend weight + increment_kg at the bottom of the rep range.
   - Otherwise: recommend the same weight with one more rep on the weakest set, and give an alternative of weight + increment_kg at the bottom of the rep range.
   - Worked example with rep_range 6-12 and increment 2.5: 'Last session: 80 kg for 3x8 at RPE 8. Target: 80 kg for 3x9, or 82.5 kg for 3x6.'
2. linear_progression(last_session_sets, weekly_increment_kg): add a fixed increment each week while all prescribed reps were completed; hold the weight after a failed session.
3. Default increments as editable constants: 2.5 kg upper-body compounds, 5 kg lower-body compounds, 1.25 kg isolation work.
4. detect_plateau(history, sessions=3): true when estimated 1RM (Epley: weight * (1 + reps/30)) has not improved across the last N sessions. Add deload_suggested when RPE is also trending up.
5. weekly_volume(sets, catalog, week_start): effective sets per muscle group for one week. An effective set is a working set at RPE 6 or higher (editable constant). Return each muscle with its set count and a status of 'below', 'in_range' or 'above' against a range of 10-20 sets per week.
6. A Recommendation dataclass: weight_kg, rep_target, alternative, reason (plain-language string), plateau_flag, deload_suggested.

Tests: the exact 80 kg example above, an increase after hitting the top of the range, a hold after missed reps, plateau detection on a flat series and on a rising series, the Epley formula, and weekly volume bucketing across week boundaries.

Prompt 5.1: Ingestion pipeline
Build the ingestion half of the RAG pipeline in app/modules/rag_core/ (an ingest.py module imported by engine.py).

1. PDFs live in backend/docs/. Create backend/docs/manifest.json mapping each file name to a category: 360Nutritionprogram1.pdf and NNC_2016_Newsletter_1.pdf -> 'nutrition'; BodyType+Training+and+Nutrition.pdf, Functional-Training-Guide-IAFS.pdf and EndomorphEvolution.pdf -> 'exercise'. If a PDF is in the folder but missing from the manifest, stop with a clear error instead of guessing.
2. Extract text page by page with pypdf. If a page has fewer than 50 characters, log a warning that it may be scanned, and count such pages per file.
3. Chunk each page into about 900 characters with 150 characters of overlap, splitting on paragraph boundaries first, then sentences. Each chunk stores chunk_id, text, source (file name), page and category.
4. Embed chunks in batches with the sentence-transformers model from settings.EMBEDDING_MODEL, using normalised vectors.
5. Build one FAISS IndexFlatIP per category and save it as vectorstore/{category}.faiss, with a sidecar vectorstore/{category}_chunks.json holding the chunk metadata in the same order.
6. Make ingestion idempotent: store a SHA-256 hash of each PDF in vectorstore/state.json and re-embed only changed files, rebuilding the affected category index.
7. CLI: python -m app.modules.rag_core.ingest [--rebuild]. Print files processed, pages, chunks per category and warnings.

Tests use two tiny generated PDFs and a fake hash-based embedder, so they need no model download. Cover manifest errors, chunk size and overlap, the hash skip on a second run, and the rebuild flag.
